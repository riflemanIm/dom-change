# План локального ручного тестирования DomObmen

## 1. Цель

Проверить весь реализованный пользовательский путь в условиях, близких к реальной работе:

```text
регистрация → подтверждение email → профиль → объявление → фото → доступность
→ модерация → каталог → избранное → заявка → чат → подтверждение
→ ДомБаллы → завершение → отзывы и уведомления
```

План рассчитан на последовательный ручной прогон. Автоматические тесты запускаются перед ним как smoke-проверка.

## 2. Тестовые роли и браузерные сессии

Не следует переключать аккаунты в одной вкладке: это скрывает ошибки cookie, React Query cache и сокетов. Использовать разные профили браузера либо обычное окно и несколько разных браузеров.

| Сессия | Роль | Назначение |
| --- | --- | --- |
| Browser A | `USER`, хозяин | Создаёт и публикует дом, принимает заявку |
| Browser B | `USER`, гость | Ищет дом, добавляет в избранное, отправляет заявку |
| Browser M | `MODERATOR` | Проверяет очередь модерации и принимает решение |
| Browser Admin | `ADMIN` | Проверяет доступ администратора и модератора |
| Anonymous | Без входа, приватное окно | Проверяет публичные страницы и запрет приватных действий |

Для Browser A можно использовать подготовленного пользователя. Browser B лучше зарегистрировать заново через интерфейс — так одновременно проверяется регистрация и Mailpit. Администратор создаётся seed-скриптом из `SEED_ADMIN_EMAIL` и `SEED_ADMIN_PASSWORD`. Перед тестом нужно убедиться, что отдельному аккаунту действительно назначена роль `MODERATOR`.

Пароли и реальные email не записывать в отчёт, скриншоты или Git.

## 3. Подготовка окружения

### 3.1. Запуск

```bash
cp .env.example .env
npm install
docker compose up -d
npm run prisma:generate --workspace server
npm run prisma:migrate --workspace server
npm run prisma:seed --workspace server
npm run dev
```

Если `.env` уже настроен, копировать его заново не нужно.

Проверить сервисы:

| Сервис | Адрес | Ожидаемый результат |
| --- | --- | --- |
| Client | http://localhost:3000 | Главная страница |
| API | http://localhost:4000/api/v1 | API доступен; корневой маршрут может вернуть 404 |
| Swagger | http://localhost:4000/docs | Список API-операций |
| Mailpit | http://localhost:8025 | Локальные письма |
| MinIO | http://localhost:9001 | Консоль объектного хранилища |
| PostgreSQL | `localhost:5433` | Контейнер healthy |
| Redis | `localhost:6379` | Контейнер healthy |

Команды диагностики:

```bash
docker compose ps
docker compose logs --tail=100 postgres redis minio mailpit
```

Все контейнеры должны иметь состояние `running` или `healthy`.

### 3.2. Автоматический smoke-test

```bash
npm run lint
npm run test
npm run test:integration --workspace server
npm run build
```

Ручное тестирование начинать после успешных lint, unit/integration tests и production build. Если интеграционные тесты используют общую локальную БД, сначала проверить их конфигурацию: они не должны удалять данные ручного стенда.

### 3.3. Тестовые данные

Для проверки seed-карточек установить:

```env
INCLUDE_FAKE_PROPERTIES=true
```

После изменения перезапустить server. Для отдельной проверки скрытия fake-карточек вернуть `false`.

Подготовить изображения:

- валидный JPEG до 5 МБ для аватара;
- валидные JPEG, PNG и WebP до 10 МБ для жилья;
- файл больше лимита;
- текстовый файл с расширением `.jpg` для негативной проверки MIME-типа.

### 3.4. Фиксация результата

Для каждого пункта отмечать:

```text
[PASS/FAIL/BLOCKED] ID теста
Аккаунт:
Шаги:
Ожидаемо:
Фактически:
Console/Network:
Скриншот:
```

При ошибке сохранять URL, HTTP method/status, response body и ошибки Console. Секреты и токены перед публикацией замазывать.

## 4. Smoke-тест публичной части

### PUB-01. Главная

- Открыть `/` без авторизации.
- Проверить шапку, логотип, hero-слайдшоу, поиск, «Как это работает», карточки, CTA и футер.
- Дождаться автоматической смены hero-изображения.
- Проверить ручную навигацию с клавиатуры и отсутствие скачков макета.
- Ожидаемо: нет ошибок Console, изображения не ломаются, ссылки ведут на существующие страницы.

### PUB-02. Адаптивность

- Проверить ширины примерно 375, 768, 1024 и 1440 px.
- Ожидаемо: нет горизонтального скролла; формы, карточки, меню и текст не перекрываются; на `lg` каталог показывает три колонки.

### PUB-03. Статические разделы

- Открыть `/help`.
- Перейти по всем ссылкам оглавления и ссылкам помощи из Header/Footer.
- Ожидаемо: якоря прокручивают к правильным разделам, внутренних 404 нет.

### PUB-04. Анонимные ограничения

- Без входа открыть `/account`, `/account/homes`, `/account/exchanges`, `/admin/moderation`.
- Попытаться добавить карточку в избранное и отправить заявку.
- Ожидаемо: приватные страницы/действия требуют входа; данные других пользователей не показываются.

## 5. Регистрация и авторизация

### AUTH-01. Валидация регистрации

- Проверить пустые поля, неверный email, короткий пароль, пароль без буквы и без цифры.
- Ожидаемо: понятные сообщения, запрос с невалидными данными не отправляется либо API возвращает контролируемый `400`.

### AUTH-02. Успешная регистрация Browser B

- Зарегистрировать нового пользователя.
- Ожидаемо: пользователь авторизован, в Header отображается имя/аватар, доступно 500 приветственных ДомБаллов в текущей конфигурации.
- Проверить Mailpit: письмо подтверждения получено один раз и содержит рабочий код/ссылку.

### AUTH-03. Подтверждение email

- Ввести неверный код, затем правильный.
- Проверить повторную отправку и её rate limit.
- Ожидаемо: неверный код не подтверждает email; правильный подтверждает и начисляет 100 ДомБаллов один раз; повторное применение не начисляет бонус снова.

### AUTH-04. Вход и выход

- Выйти, войти с неверным и правильным паролем.
- Обновить страницу после успешного входа.
- Ожидаемо: неверные данные дают `401` без раскрытия существования email; после reload сессия восстанавливается; после logout приватные запросы недоступны.

### AUTH-05. Несколько сессий

- Войти одним пользователем в двух браузерах.
- Выполнить обычный logout в одном: вторая сессия должна остаться рабочей.
- Снова войти и выполнить «выйти на всех устройствах», если действие доступно.
- Ожидаемо: все access/refresh-сессии пользователя перестают работать, сокеты отключаются.

### AUTH-06. Восстановление пароля

- Запросить восстановление для существующего и несуществующего email.
- Проверить, что ответы не позволяют определить наличие аккаунта.
- Открыть ссылку из Mailpit, задать новый пароль.
- Повторно использовать ту же ссылку.
- Ожидаемо: пароль меняется один раз; старая ссылка и прежние сессии недействительны; старый пароль не работает.

## 6. Профиль

### PROF-01. Просмотр и редактирование

- Открыть `/account/settings`.
- Изменить имя и остальные доступные поля.
- Обновить страницу.
- Ожидаемо: изменения сохранены и сразу видны в Header.

### PROF-02. Аватар

- Загрузить валидное изображение.
- Проверить preview, Header и страницу после hard reload.
- Проверить большой и неверный файл.
- Ожидаемо: валидный аватар хранится в MinIO и отображается по доступному URL; невалидные файлы отклоняются; CORS-ошибок нет.

## 7. Объявление хозяина

Выполняется в Browser A.

### HOME-01. Черновик и мастер

- Создать жильё через `/account/homes/new`.
- Пройти все 10 шагов: тип, адрес, характеристики, удобства, правила, описание, ДомБаллы, фото, доступность, проверка.
- На каждом шаге проверить обязательные поля и граничные значения.
- Ожидаемо: ошибки понятны; введённые данные не пропадают при переходах и reload; чужой пользователь не может открыть edit URL.

### HOME-02. Фото

- Загрузить минимум три фото разных поддерживаемых форматов.
- Изменить порядок и главное фото, удалить второстепенное.
- Во время загрузки проверить индикатор и запрет преждевременной отправки.
- Ожидаемо: signed upload проходит через MinIO, сервер завершает обработку, preview отображается; порядок стабилен после reload.

### HOME-03. Доступность

- Создать период с типом `BOTH`, ценой за ночь, min/max nights и max guests.
- Проверить пересекающиеся периоды, неверный диапазон дат и удаление периода.
- Ожидаемо: невалидные диапазоны отклоняются, валидный период влияет на каталог и форму заявки.

### HOME-04. Отправка на модерацию

- До подтверждения email попытаться отправить объявление.
- После подтверждения отправить корректное объявление.
- Попытаться редактировать его во время модерации.
- Ожидаемо: неподтверждённый email и неполное объявление блокируют отправку; статус становится `PENDING_MODERATION`; редактирование временно запрещено.

## 8. Модерация и роли

### MOD-01. Проверка RBAC

- Browser A/B: открыть `/admin/moderation` и вызвать moderation API через Swagger с USER token.
- Browser M/Admin: открыть ту же страницу.
- Ожидаемо: USER получает `403`; MODERATOR и ADMIN видят очередь.

### MOD-02. Возврат на доработку

- Модератор возвращает объявление с комментарием.
- Browser A получает уведомление, исправляет объявление и отправляет снова.
- Ожидаемо: комментарий виден владельцу, статус корректно меняется, повторная отправка появляется в очереди.

### MOD-03. Публикация

- Одобрить исправленное объявление.
- Ожидаемо: статус `PUBLISHED`, уведомление приходит владельцу, объявление появляется в публичном каталоге и открывается по slug.

### MOD-04. Конкурентное решение

- Открыть одну заявку модерации в Browser M и Admin.
- Принять решение в одном браузере, затем попытаться принять другое во втором.
- Ожидаемо: второе устаревшее действие не перезаписывает первое и возвращает контролируемый конфликт.

## 9. Каталог, фильтры и карточка

### CAT-01. Поиск локации

- Медленно и быстро вводить город в Autocomplete.
- Очистить поле, выбрать вариант клавиатурой.
- В Network проверить debounce и отмену старых запросов.
- Ожидаемо: старые ответы не перезаписывают новые; нет CORS и `AbortError` для пользователя.

### CAT-02. Фильтры

- Проверить город, диапазон дат, 1 и 10 гостей, вид обмена, стоимость, тип жилья, спальни, детей, животных и удобства.
- Проверить невозможный диапазон и дату выезда раньше заезда.
- Ожидаемо: URL отражает фильтры, reload сохраняет результат, карточки соответствуют всем активным условиям.

### CAT-03. Сортировка и пагинация

- Переключить каждый вид сортировки и несколько страниц.
- Ожидаемо: нет повторов/пропусков, число страниц соответствует total, сортировка стабильна.

### CAT-04. Детальная страница

- Открыть жильё по slug с главной и каталога.
- Проверить галерею, характеристики, хозяина, доступность и кнопку заявки.
- Ожидаемо: маршрут не даёт 404, приватный точный адрес публично не раскрывается.

### CAT-05. Fake-карточки

- С `INCLUDE_FAKE_PROPERTIES=true` убедиться, что seed-карточки видны.
- Вернуть `false`, перезапустить сервер и повторить поиск.
- Ожидаемо: fake-карточки полностью исчезают из каталога и подсказок.

## 10. Избранное и сохранённые поиски

### FAV-01. Избранное

- Browser B добавляет карточку, повторно нажимает кнопку, проверяет `/account/favorites` и reload.
- Удаляет карточку из списка.
- Ожидаемо: состояние синхронно в каталоге и аккаунте, дубликатов нет, собственное жильё добавить нельзя.

### SEARCH-01. Сохранённый поиск

- Настроить несколько фильтров, сохранить под именем, применить сохранённый поиск и удалить его.
- Проверить одинаковое имя и пустой поиск.
- Ожидаемо: восстановлены все параметры, действия доступны только владельцу.

## 11. Полный обмен за ДомБаллы

Browser A — хозяин опубликованного дома, Browser B — гость.

### EX-01. Создание заявки

- Browser B выбирает свободные даты в пределах min/max nights и допустимое число гостей.
- Запоминает баланс и отправляет заявку `POINTS`.
- Ожидаемо: статус `PENDING`; баланс ещё не изменён; хозяину приходит realtime-уведомление; заявка видна обоим.

### EX-02. Негативные условия

- Проверить прошедшие даты, слишком короткую/длинную поездку, превышение гостей, недоступный период, собственное жильё и пересекающуюся активную заявку.
- Ожидаемо: API отклоняет каждый случай независимо от клиентской валидации.

### EX-03. Предварительное одобрение

- Browser A открывает заявку и нажимает предварительное одобрение.
- Ожидаемо: статус `PREAPPROVED`, Browser B получает уведомление без reload.

### EX-04. Подтверждение и резерв

- Browser B подтверждает заявку.
- Ожидаемо: статус `CONFIRMED`; `стоимость за ночь × ночи` перемещается из available в reserved; итог нельзя подменить через DevTools; даты блокируются для других подтверждений.

### EX-05. Недостаточный баланс

- Для отдельной заявки использовать стоимость выше доступного баланса либо тестовый аккаунт с малым балансом.
- Ожидаемо: подтверждение отклонено, статус и журнал транзакций не изменились частично.

### EX-06. Завершение

- Для локального теста использовать поездку, дата выезда которой уже наступила, либо подготовить данные контролируемым seed/fixture.
- Завершить обмен одним из участников.
- Ожидаемо: статус `COMPLETED`; reserved уменьшается у гостя, хозяин получает баллы, появляются согласованные записи журнала и увеличивается счётчик завершённых обменов.

## 12. Прямой обмен

Оба пользователя должны иметь опубликованные дома с `acceptsDirect=true` и свободными периодами.

### DIRECT-01. Создание

- Browser B выбирает `DIRECT` и предлагает своё опубликованное жильё.
- Ожидаемо: без подходящего собственного дома заявку создать нельзя; подходящий дом прикреплён к заявке.

### DIRECT-02. Жизненный цикл

- Провести заявку через `PENDING → PREAPPROVED → CONFIRMED → COMPLETED`.
- Ожидаемо: ДомБаллы не резервируются и не списываются; периоды обоих домов защищены от конфликтующей подтверждённой заявки.

## 13. Чат и realtime

### CHAT-01. Два участника онлайн

- Открыть один обмен одновременно в Browser A и B.
- Отправлять сообщения по очереди, включая кириллицу, emoji и многострочный текст.
- Ожидаемо: сообщение появляется у второй стороны без reload, порядок одинаковый, дубликатов нет.

### CHAT-02. Непрочитанные сообщения

- Закрыть диалог в Browser B, отправить сообщение из A.
- Ожидаемо: обновляется счётчик непрочитанных/уведомление; после открытия сообщение отмечается прочитанным.

### CHAT-03. Ограничения

- Отправить пустое сообщение и текст длиннее 4000 символов.
- Попытаться обратиться к чату третьим пользователем.
- Ожидаемо: валидация блокирует текст, не являющийся участником пользователь получает `403/404` без содержимого переписки.

### CHAT-04. Переподключение

- Отключить сеть в DevTools, отправить/получить сообщение после восстановления.
- Перезапустить server при открытом клиенте.
- Ожидаемо: сокет переподключается, история догружается через API, сообщения не теряются и не дублируются.

## 14. Отмена и отклонение

### CANCEL-01. До подтверждения

- Гость отменяет `PENDING`; в другой заявке хозяин отклоняет `PENDING/PREAPPROVED`.
- Ожидаемо: правильный финальный статус и realtime-уведомление, ДомБаллы не меняются.

### CANCEL-02. После подтверждения

- Подтвердить POINTS-заявку, затем отменить с причиной.
- Проверить короткую/пустую и валидную причину.
- Ожидаемо: требуется причина допустимой длины, reserved полностью возвращается в available, повторная отмена не создаёт второй возврат.

### CANCEL-03. Конкурентные действия

- Почти одновременно отменить/подтвердить одну заявку в двух браузерах.
- Ожидаемо: выполняется только допустимый переход состояния, нет двойного резерва или возврата.

## 15. Отзывы и рейтинг

### REVIEW-01. Ограничения

- Попытаться оставить отзыв до `COMPLETED`, от третьего пользователя и второй отзыв от того же участника.
- Ожидаемо: все действия отклонены.

### REVIEW-02. Взаимные отзывы

- После завершения обе стороны выставляют общую оценку, чистоту, общение и комментарий.
- Проверить границы 1–5 и длину комментария.
- Ожидаемо: отзывы сохранены, рейтинг пересчитан, персональные данные не появляются автоматически.

## 16. Уведомления

### NOTIF-01. Источники

- Проверить уведомления о новой заявке, изменении статуса, сообщении, модерации и отзыве.
- Ожидаемо: корректный получатель, ссылка ведёт к объекту, событие не дублируется.

### NOTIF-02. Прочтение

- Отметить одно уведомление и затем все прочитанными.
- Обновить страницу и открыть второй браузер той же сессии.
- Ожидаемо: состояние сохраняется на сервере и синхронизируется.

## 17. ДомБаллы и журнал

### POINTS-01. Инварианты

- На каждом этапе полного обмена фиксировать `available`, `reserved`, `bonus` и строки истории.
- Ожидаемо: баланс никогда не отрицательный; сумма не создаётся и не исчезает; одна бизнес-операция не проводится дважды.

### POINTS-02. Идемпотентность

- Дважды быстро нажать подтверждение/завершение либо повторить одинаковый запрос в Network.
- Ожидаемо: только одна транзакция резерва, списания и начисления.

## 18. Управление объявлениями

### LIFE-01. Скрытие и восстановление

- Скрыть опубликованное объявление и проверить каталог.
- Восстановить его.
- Ожидаемо: скрытое жильё недоступно публично, после восстановления возвращается без потери данных.

### LIFE-02. Изменение опубликованного объявления

- Изменить существенное поле опубликованного дома.
- Ожидаемо: объявление возвращается в предусмотренный статус черновика/повторной модерации и не продолжает публично показывать непроверенные изменения.

### LIFE-03. Архивирование

- Проверить архивирование без активной заявки и при `PENDING`, `PREAPPROVED`, `CONFIRMED`.
- Ожидаемо: активный обмен блокирует архивирование; разрешённое архивирование убирает жильё из каталога, восстановление создаёт редактируемый черновик.

## 19. Безопасность и доступ к чужим объектам

В DevTools или Swagger заменить ID на объект другого пользователя:

- редактирование и отправка объявления;
- фото и периоды доступности;
- сохранённый поиск;
- уведомление;
- заявка и чат;
- отзыв.

Ожидаемо: `403` либо безопасный `404`; чужие данные не возвращаются. Дополнительно проверить:

- лишние поля DTO дают `400`;
- неверный UUID даёт `400`, а не `500`;
- HTML/JS в имени, описании, чате и отзыве отображается как текст;
- точный адрес отсутствует в публичном API до подтверждения;
- refresh cookie имеет `HttpOnly`, `SameSite=Strict`, правильный `Path`; в production также `Secure`;
- CORS разрешает настроенный client origin и отклоняет посторонний origin;
- повторные запросы входа, регистрации, reset и email verification достигают `429`.

## 20. Финальная проверка качества

- Во всём прогоне нет необработанных `500`, hydration errors и красных ошибок Console.
- Loading/error/empty states видны и понятны.
- Кнопки блокируются во время запроса и не создают повторных операций.
- Route loading bar появляется при переходах и исчезает после завершения.
- После hard reload состояние берётся с сервера, а не существует только в React state/cache.
- Русские тексты не содержат опечаток и технических сообщений Prisma/NestJS.
- Основные действия доступны с клавиатуры; у интерактивных иконок есть accessible name.

## 21. Рекомендуемый порядок прогона

Чтобы не пересоздавать данные, выполнять разделы так:

1. Окружение и автоматический smoke-test.
2. Публичная часть.
3. Регистрация Browser B, email и профиль.
4. Browser A создаёт объявление.
5. Browser M возвращает его на доработку, затем публикует.
6. Browser B проверяет каталог, фильтры, избранное и сохранённый поиск.
7. Полный обмен за ДомБаллы с чатом и уведомлениями.
8. Отзывы после завершения.
9. Второй обмен для сценария отмены.
10. Два дополнительных опубликованных дома для прямого обмена.
11. Проверки ролей, чужих ID, rate limit и конкурентных запросов.
12. Скрытие, восстановление и архивирование объявлений.
13. Финальный responsive/accessibility regression.

## 22. Критерии готовности к тестовому деплою

- Нет открытых дефектов уровня Critical и High.
- Полный POINTS-обмен и DIRECT-обмен проходят от начала до конца.
- Резерв, возврат и перевод ДомБаллов сходятся по журналу.
- USER не получает доступ к модерации или чужим данным.
- Загрузка фото, email и realtime работают после чистого запуска окружения.
- Production build проходит повторно после исправлений.
- Известные Medium/Low-дефекты записаны с понятным workaround и приоритетом.
